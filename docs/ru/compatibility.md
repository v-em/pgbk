# Совместимость, обновление и подтверждения

Версия 0.3.3 исправляет выбор начальной базы pg_dumpall, выгружает globals до баз и безопасно классифицирует распознанные ошибки прав в streaming. Прошли 194 модульных теста и [пять проверок globals на реальном PostgreSQL](../../tests/reports/globals-033.json) внутри Linux amd64 worker PostgreSQL 18 без внешней сети. Direct/staged проверены с ролью без SUPERUSER и без CONNECT к postgres/template1, включая буквальное имя служебной базы. Живой managed-сервис не проверялся; ограничения системных баз Yandex описаны в [эксплуатации](operations.md).

Версия 0.3.2 добавляет полное руководство восстановления, инструкции конкретной копии и endpoints targets в общем Secret. Локально прошли 191 модульный тест, проверка двуязычной документации/версий и Helm lint/render с overlay общего подключения. Собран Linux amd64 worker PostgreSQL 18 `pgbk-worker:18-0.3.2`; без сети проверены версия CLI, оба включённых руководства, поля подключения из проекции Secret и генерация инструкций. Новая интеграционная матрица 14–18 и живое восстановление в managed для 0.3.2 не запускались. Исторические подтверждения ниже сохраняют исходные версии выпуска.

Версия 0.3.1 реализует фильтры схем и исключения таблиц расширений. [Проверка схем и pg_cron](../../tests/reports/schema-selection-minikube18.json) использует PostgreSQL 18.1 с pg_cron 1.6 и инструменты worker 18.6. [Регрессия](../../tests/reports/spec13-minikube18-031.json) использует PostgreSQL 18.6. [Модульные тесты](../../tests/reports/schema-unit.json) проверяют новые настройки и контроль архива.

**Локальная реализация спецификации 1.3:** [Ручная проверка](verification.md) описывает зафиксированную политику, неизменяемые попытки, reconciliation сроков и два минимума retention. Новые доказательства: [PostgreSQL 18/minikube](../../tests/reports/spec13-minikube18.json) и [unit-тесты](../../tests/reports/unit-spec13.json). Локальные проверки PostgreSQL 17.11 на 1 и 20 GiB прошли для logical и physical backup с последующим восстановлением при остановленном источнике. Отчёты содержат версии утилит, время, пики scratch и RSS. Тест на 20 GiB выполнялся в контейнере с 2 CPU и 4 GiB RAM: наблюдаемый пик scratch — 42,04 GiB, суммарного RSS процессов — 0,97 GiB. Fixture хранится без сжатия PostgreSQL, но содержит хорошо сжимаемый повторяющийся текст. ## Повторение проверок разработки

Запустите Moto в отдельном терминале только с синтетическими учётными данными, затем подготовьте одноразовый bucket pgbk-test. Не направляйте fixture-скрипты в production: harness создаёт синтетические базы и использует отдельные integration-префиксы.

```sh
uv sync --frozen --group integration
uv run --frozen --group integration python -m pytest
uv run --frozen --group integration python scripts/check_docs.py
helm lint charts/pgbk -f examples/values.yaml
uv run --frozen --group integration moto_server -H 0.0.0.0 -p 19000
```

```sh
uv run --frozen --group integration python tests/feasibility/bucket.py
python3 scripts/build_images.py
python3 scripts/run_integration.py
python3 scripts/evidence.py
```

Для Docker Linux нужен host.docker.internal:host-gateway; runner добавляет его автоматически. Kubernetes smoke использует отдельно созданный kind-кластер и удаляет временные namespace. CI выполняет зафиксированные unit/chart-проверки и ту же реальную матрицу 14–18, не публикуя образы и не выполняя живых действий провайдеров.

## Обновление и артефакты

До обновления сохраните проверенную скачиваемую копию и среду восстановления соответствующей основной версии. Сборку и публикацию образов выполняйте своим registry-процессом, записывая реальные registry digest и обновляя values/images. Docker image config ID не заменяет digest registry-манифеста. Новые immutable ConfigMap применяются только к новым Job; запущенные сохраняют прежнюю ссылку. Проекции Secret управляются извне и могут изменяться во время запуска, поэтому выполняйте ротацию между запусками. Сохранённые Lease нельзя сбрасывать при upgrade/rollback; общие заранее созданные Lease требуют coordination.createLeases=false. Стабильные installationId/sourceId/profileId/prefix сохраняют идентичность каталога. Их изменение выбирает другой каталог, а не выполняет миграцию.

Wheel/source archive CLI, Helm package, сведения об образах, checksums, CycloneDX SBOM и уведомления о сторонних компонентах создаются в dist. Исходный код лицензирован AGPL-3.0-only. PostgreSQL/WAL-G/Python/OS и Python-зависимости сохраняют собственные лицензии; copyright Debian и тексты лицензий пакетов сохраняются/извлекаются. Обогащение Go-лицензий и неизвестные записи SBOM требуют окончательного аудита до сертификации распространения; результат сканера не является юридическим заключением. Базы PostgreSQL/WAL-G/Python-зависимости зафиксированы, но apt-репозитории и время сборки не заморожены для побитового повторения. Продвигайте проверенный образ по immutable registry digest, не пересобирая его при установке.

## Приёмка Yandex оператором

Используйте заранее созданные изолированные источники/назначения/префиксы bucket и учётные данные, поступающие извне. Выполните T-001–T-004, T-024, T-028, T-030–T-032 и T-035 из [плана тестирования](test-plan.md): backup, удалённую SHA-проверку, скачивание, восстановление при недоступном источнике, drill, отказы доступа/TLS и ограниченный retention. Сохраните версии утилит/образов/chart, run ID, точный endpoint провайдера, ожидаемые данные и обезличенные отчёты времени/ресурсов. Удаляйте только свои временные префиксы/claim после подтверждения отсутствия writer. Репозиторий не выполняет живые тесты Yandex и не сертифицирует их по результатам эмулятора.

Отчёты от 2026-10-11 — историческая база 0.1. Проверки режимов 0.2 записываются отдельно в tests/reports/modes-*.json. Прежние license/SBOM-артефакты не подтверждают новую сборку.
