# Веб-интерфейс pgbk v1

Проект спецификации от 6 ноября 2026 года. Базовая версия для интеграции — pgbk 0.3.3. Основой для разработки и приёмки служит [английская спецификация](../en/ui-v1.md). Русский перевод предназначен для ознакомления.

Администратор выбирает профиль, проверяет время следующего планового бэкапа, запускает разовый backup и переходит из Job к опубликованным артефактам и инструкции по восстановлению этой копии. В навигации три раздела — **Копии**, **Расписания**, **Задания**. На каждом экране видны профиль и источник. Единственная операция записи при управлении бэкапами через UI v1, — запуск backup.

## Интеграция с pgbk 0.3.3

Для логических профилей с `logical.globals: enabled` worker выгружает globals до архивов баз и явно передаёт `targets.<id>.maintenanceDatabase` в pg_dumpall. В подтверждении запуска профиля показывать настроенную политику globals и служебную базу из конфигурации, на которую ссылается шаблон, включая значение по умолчанию `postgres`, если поле отсутствует. Имя базы отображать буквально. Изменения конфигурации выполняются через существующий процесс развёртывания. См. [требования и диагностику выгрузки globals](operations.md#ошибки-выгрузки-globals).

Ошибка выгрузки globals запрещает публикацию копии. Распознанные ошибки прав или аутентификации как в direct, так и в staged приводят к `ACCESS_DENIED`. Показывать записанный код причины и ссылку на требования к источнику. Администратору следует проверить настроенную служебную базу и доступ роли резервного копирования. Для исторических записей с общим `TOOL_FAILED` показывать сохранённый код с неизвестной первопричиной.

В 0.3.3 итоговая JSON-ошибка в stderr worker содержит `tool` и `toolExitCode`, когда они доступны, а сохранённые терминальные события S3 содержат `reasonCode` и `failedPhase`. Карточка Job v1 использует сохранённые поля. Для дополнительных сведений об инструменте в будущем потребуется адаптер структурированной диагностики. Ошибку worker `ACCESS_DENIED` отличать от отклонённой сессии UI или запрещённой операции API интерфейса.

Контрактами интеграции служат схема артефактов версии 1, маркеры публикации и инструкции для каждой копии. Принимать старые копии, прошедшие проверку формата, и использовать их сохранённые инструкции. Выполненные проверки 0.3.3 описаны в [сведениях о совместимости](compatibility.md).

## Установка и доступ

- Отдельные образ и Helm chart `pgbk-ui`, собственные Deployment, Service, ServiceAccount и цикл обновлений. Один экземпляр обслуживает одну установку pgbk в одном кластере. При остановке или удалении UI плановые Job продолжают работать. Удаление UI затрагивает только его ресурсы.
- Для v1 достаточно одной реплики и SQLite на выделенном PVC для журнала ручных запросов и индекса каталога. Перезапуск Pod сохраняет журнал. Индекс можно перестроить из S3. Устанавливать обновление с одной активной репликой.
- Браузер обращается по HTTPS к серверу UI. Сервер читает Kubernetes API и S3, отдаёт страницы и API одного origin. Администратор задаёт installationId, Helm release, namespace, доступные профили, соответствующие источники и разрешённые S3-префиксы в конфигурации установки UI. Сверять профиль и sourceId с конфигурацией pgbk, на которую ссылается текущий backup CronJob. Расхождение блокирует запуск по этому профилю и выводится в «Расписаниях».
- В v1 одна учётная запись приложения — **Администратор**. Ему доступны чтение данных настроенной установки и запуск бэкапов по разрешённым профилям. Для каждого запроса данных и запуска, включая прямые ссылки и повторы, требуется действующая сессия администратора. Сервер проверяет установку, профиль, namespace и разрешённое действие.
- Имя пользователя и пароль администратора хранятся вместе в отдельном для установки секрете Vault KV. В Helm values указываются только адрес Vault, роль для входа в Vault и путь секрета. Сервер UI обращается в Vault от своего Kubernetes ServiceAccount с правом чтения этого секрета. Администратор вводит данные по HTTPS. Сервер сверяет их с текущими значениями в Vault, ограничивает частоту попыток входа и возвращает общую ошибку при неверных данных. Учётные данные исключаются из Git, Helm-релизов, SQLite, хранилища браузера и логов.
- При входе сервер создаёт сессию с ограниченным сроком действия и передаёт непрозрачный идентификатор в cookie с Secure, HttpOnly и SameSite. Сессия привязана к версии секрета в Vault. Перед авторизацией каждого защищённого запроса сервер сверяет текущую версию. Смена секрета отзывает старые сессии и учётные данные. Если сверка невозможна, отклонить запрос и сообщить о временной недоступности авторизации. Выход отзывает сессию. Запросы записи из браузера защищены от CSRF. В аудите фиксируются имя вошедшего администратора и requestId.
- Сервер получает отдельные read-only credentials S3 для списка ключей и чтения метаданных каталога и указанных для каждой копии инструкций по восстановлению. Рабочие ключи S3 и учётные данные PostgreSQL остаются у worker. В Kubernetes разрешить чтение нужных CronJob, Job и именованных ConfigMap. Право создания Job предоставить только в namespace резервирования и только при включённом ручном запуске. Поскольку RBAC разрешает создание Job во всём namespace, для этой identity обязательна admission-проверка соответствия спецификации Job доверенному backup-шаблону, включая image, command/args, SA, env и volumes. При отсутствии ограничения установить UI в режиме просмотра. UI не требует прав на Secrets, изменение CronJob, Lease или доступ к Pod logs.

## Копии и карточка артефакта

Источник данных — каталог `<prefix>/v1/<installationId>/<sourceId>/<profileId>/`. Ключ копии в UI включает всю эту область и `runId`. В таблице показать время завершения с часовым поясом, профиль, источник, тип, запуск вручную/по расписанию, размер и результат проверки восстановлением. Сортировка по `completedAt` и `runId` от новых к старым, при совпадении — по области. Фильтры по профилю, источнику, типу и времени. Из строки открывается карточка по постоянной ссылке.

Копия попадает в опубликованные после сверки `runs/<runId>/complete.json` с `manifest.json` по версии, области, runId, времени и SHA-256 байтов манифеста. Применяются правила формата каталога pgbk. Проверять отсутствие `deletion.json`, в том числе при повторном открытии карточки. Ошибки структуры или хеша вывести отдельно с runId и кодом причины. Запуск только с событиями может отображаться в диагностике. При удалении копии по retention открытая ссылка показывает «Копия удалена или недоступна».

| Часть карточки | Что видит администратор |
|---|---|
| Сводка | runId, начало и завершение, длительность, тип, версия PostgreSQL, образ worker, число файлов и суммарный размер. Время снимка и основание оценки выводятся отдельно от времени завершения, для logical доступны значения по базам. |
| Артефакты | Для каждого файла — fileId, имя, назначение, формат, размер в байтах и полный SHA-256 из манифеста. Строка открывает JSON соответствующего элемента `artifacts[]`. Для logical показать базу, полный или выборочный охват, параметры сжатия и передачи, сохранённую выборку, инвентарь и известные зависимости, если они записаны. |
| Метаданные | Отдельные представления сохранённых `manifest.json`, `complete.json` и сведений о проверке из `verification/<runId>/`. Показывать структурированный JSON с поиском по ключу, доступный только в границах профиля. Использовать серверную проекцию разрешённых полей, обозначать скрытые поля, экранировать текст. Маскировать внутренние адреса, ссылки на Secret и SQL выборки/проверок, в том числе во вложенных объектах. Для старых манифестов отсутствующие поля помечать «Нет данных». |
| Проверка восстановлением | Применять расчёт состояния pgbk к политике, зафиксированной в копии, и записям попыток. Показывать срок, активную и последнюю завершённую попытки, результат и причину. Публикация копии, выполнение Job и проверка восстановлением имеют отдельные индикаторы. |

Чтение списка и карточек использует ограниченные по размеру JSON и проверку метаданных уровня `Catalog.describe(verify=False, check_objects=False)`. Полный `Catalog.list()/view()` в 0.3.3 перечитывает архивы, поэтому для UI нужен отдельный путь чтения. Отметка «Манифест проверен» относится к сверке с маркером публикации. У файла явно подписать «SHA-256 из манифеста». Для списка нужен постраничный API и фоновое обновление индекса метаданных по разрешённым префиксам с ограниченным параллелизмом. Указывать время обновления. Ошибку одного префикса показывать рядом с ним, сохраняя доступ к остальным данным. Пока первый обход не завершён, обозначать неполноту списка.

## Вкладка «Порядок восстановления»

Источник вкладки — инструкция, опубликованная с выбранной копией. В 0.3.3 worker записывает в S3 английский файл `runs/<runId>/recovery/BACKUP-RESTORE.md` и русский `BACKUP-RESTORE.ru.md` в том же каталоге. До публикации `complete.json` worker проверяет содержимое обоих файлов в S3 и сохраняет для каждого имя, размер и SHA-256 в `manifest.json` в массиве `recoveryInstructions[]`. Инструкции описывают конкретную логическую или физическую копию. Для физической копии извлечение и проверка могут быть описаны одной командой вызова утилиты восстановления.

При открытии вкладки повторно проверить публикацию и область доступа, найти в проверенном манифесте запись для выбранного языка и прочитать из каталога recovery этой копии только соответствующий файл. До отображения безопасным текстом сверить размер (максимум 8 МиБ) и SHA-256. По умолчанию показывать английский текст с возможностью выбрать сохранённый русский перевод. Сохранить порядок разделов, имена файлов, команды и предварительные условия. Администратор может открыть рядом карточки артефактов. Порядок задаёт worker при создании копии.

Для старого манифеста без `recoveryInstructions` показать «Для этой копии инструкция не была сохранена». При отсутствии заявленного файла или ошибке проверки вывести ошибку целостности инструкции. При сбое чтения S3 сообщить о временной недоступности. В этих случаях вкладка показывает причину без генерации подменных шагов. Остальные проверенные метаданные остаются доступны.

## Расписания и разовый запуск

Показывать по одной строке на разрешённый профиль. Читать фактический CronJob `<release>-<profile>-backup` из namespace установки. Колонки — профиль, источник, тип, `spec.schedule`, `spec.timeZone`, состояние `spec.suspend`, последний запуск по расписанию из `status.lastScheduleTime` и ближайший расчётный запуск. Прогноз вычислять по cron и его зоне с учётом перевода часов. Для приостановленного расписания вывести «На паузе» без следующего времени. Отсутствующий шаблон и ошибку доступа отличать от паузы. Retention, reconcile и служебные шаблоны в расписание бэкапов не включать.

Администратор выбирает «Запустить разово» в строке профиля и подтверждает профиль, источник и тип. Приостановленный, но действительный backup-шаблон доступен для ручного запуска. После принятия запроса открыть созданную Job, показать имя, namespace и UID. Плановое время следующего запуска сохраняется.

Сервер повторно сверяет разрешения и текущий backup-шаблон, копирует его jobTemplate с зафиксированной ссылкой на ConfigMap, выставляет `pgbk.io/trigger=manual` в Job и Pod template. Вход операции ограничен profileId и ключом идемпотентности. Произвольные поля, включая host, Secret, YAML Job, cron и аргументы worker, отклоняются. Worker штатно получает Lease источника и репозитория. При занятости показать результат worker `SkippedBusy` и код причины. Успешный ответ на создание Job означает, что Kubernetes принял задание.

Требуемое расширение пути `Kubernetes.launch` — стабильная идентичность запроса вместо одного лишь `generateName`. На сервере до создания Job атомарно записать ключ, субъект, профиль и выбранную версию шаблона в устойчивый журнал запросов. Использовать детерминированное имя Job и метку запроса. При двойном клике, конкурентных запросах или потере ответа вернуть исходную Job по подтверждённой идентичности. Смена профиля с тем же ключом — конфликт. После удаления Job по TTL вернуть сохранённый результат запроса. При неопределённом исходе и исчезнувшей Job показать «Исход неизвестен» и предложить сверить события до нового осознанного запуска. Окно повтора — 24 часа, более старый ключ отклоняется по времени его выдачи сервером. Отключить запуск, если журнал недоступен. Аудит фиксирует кто, когда, по какому профилю запросил запуск, решение, requestId, имя/UID Job или код ошибки.

## Задания

Показывать Job разрешённых профилей и установки в явно разрешённых namespace, включая настроенные namespace verify/restore, если для них дан доступ. Первичный фильтр — операция backup, переключатель «Все операции» включает служебные Job. В таблице — namespace/имя, профиль, операция, инициатор (расписание/вручную/неизвестно), время создания/старта, длительность и статус. Фильтры по профилю, операции и состоянию. Карточка обновляется во время выполнения и отображает время последнего успешного чтения.

- Состояние Kubernetes определять по Job conditions и счётчикам. Терминальные Complete/Failed имеют приоритет, затем suspend, active и ожидание старта. При ошибке чтения показать недоступность. Операцию брать из `spec.template.metadata.labels["pgbk.io/operation"]`, область — из installation/profile. Для инициатора использовать аннотацию ручного запуска и ownerReference CronJob. Неоднозначное происхождение подписывать «Неизвестно».
- Отдельно отображать последнюю записанную фазу worker, время, безопасный reasonCode и фазу ошибки из событий. До появления первого события достаточно статуса Kubernetes. Связывать Job и копию по namespace и jobUid из событий каталога с runId в той же области. При отсутствии связи оставить поле пустым. Только после проверки маркера появляется ссылка «Открыть копию». В карточке копии показывать обратную ссылку на Job или её историческую запись.
- TTL и history limits ограничивают список живых Job. События S3 и журнал ручных запусков можно показывать как исторические записи с пометкой «Job удалена». Потерю доступа к API отличать от подтверждённого удаления. Полный поток логов, отмену Job, скачивание архивов, запуск restore/verify и изменение профилей или расписаний предлагается рассматривать после v1. Для будущего просмотра логов использовать контракт REQ-047 основной спецификации.

## Минимальный HTTP API

Все пути ниже имеют префикс `/api/v1` и область одной установки. Ответы со списками содержат `items`, непрозрачный `nextCursor`, время обновления и сведения о частичных ошибках. Курсор привязан к фильтрам и области доступа. Ошибки содержат безопасный код причины и requestId.

| Запрос | Результат |
|---|---|
| POST /session, DELETE /session | Войти с учётными данными администратора из Vault или завершить текущую сессию. |
| GET /profiles, GET /schedules | Разрешённые профили, доступность ручного запуска и фактические расписания. |
| GET /backups | Страница сводок опубликованных копий и отдельная диагностика. |
| GET /profiles/{profileId}/sources/{sourceId}/backups/{runId} | Метаданные, артефакты, доступные языки инструкции и результат проверки. Сервер разрешает S3-ключи внутри известной области. |
| GET /profiles/{profileId}/sources/{sourceId}/backups/{runId}/recovery/{language} | Проверенный сохранённый файл для en или ru. Код причины различает старую копию без инструкции, ошибку целостности и временную ошибку чтения. |
| POST /profiles/{profileId}/backups | С заголовком Idempotency-Key и пустым телом. 201 при создании, 200 при подтверждённом повторе, 202 при ожидающем сверки исходе. |
| GET /jobs, GET /jobs/{namespace}/{uid} | Страница заданий или карточка одного задания со связанной копией, если установлена связь. |

Сервер выдаёт ключ однократно на открытие формы подтверждения через GET /profiles/{profileId}/launch-token. Использовать ответ без кеширования. Ошибки записи включают 400 для лишних полей, 403 для запрета запуска, 409 для конфликта ключа или несовместимого шаблона и 503 при недоступности зависимости. При отсутствии действующей сессии возвращать 401, при недоступности сервиса авторизации — 503. При действующей сессии для прямого чтения за пределами разрешённой области вернуть 404.

## Приёмка v1

1. Установить UI рядом с действующей установкой 0.3.3 и удалить его. В обоих случаях периодический backup публикует копию по штатному пути.
2. На данных двух профилей и нескольких страниц проверить сортировку, переходы и границы доступа. Подмешать неверный хеш манифеста, одиночный manifest без маркера и запись удаления. В опубликованных остаются только валидные копии. По журналу запросов S3 просмотр не выполняет GET объектов artifacts/.
3. Для logical и physical сравнить содержимое вкладки с файлом на S3 для каждого языка, в том числе при расхождении порядка в инструкции с порядком массива артефактов. При переходе к другой копии показывается её собственная инструкция. Для старой копии без инструкции, отсутствующего заявленного объекта и неверного хеша проверить указанные состояния без синтеза шагов.
4. При одинаковом cron в двух зонах показать разные моменты запуска. На паузе ручной запуск разрешён администратору. Отсутствие CronJob запрещает запуск. После ручного запуска cron и suspend совпадают с исходными значениями.
5. Двойной клик, два одновременных POST, потеря ответа Kubernetes, перезапуск UI и повтор после TTL создают не более одной Job на ключ. Попытки передать параметры подключения, создать Job с изменённым шаблоном или запустить профиль вне разрешённой области отклоняются. Результат виден в аудите.
6. Проследить Job от ожидания до завершения, отдельно воспроизвести Failed и SkippedBusy. Успешный статус Job без маркера не даёт ссылку на опубликованную копию. После появления маркера переход работает в обе стороны при наличии события с UID. Повторное использование имени Job не меняет связь.
7. Отключить S3 и Kubernetes API по очереди. Рабочий источник остаётся доступным, пользователь видит причину и давность данных. Проверить прямые ссылки за пределами разрешённой области, отсутствие закрытых полей в HTTP-ответах и безопасный вывод имён БД с HTML-разметкой.
8. Проверить чтение и запуск без входа, неверные учётные данные, успешный вход администратора, выход и истёкшую сессию. После ротации секрета в Vault вход возможен только с новыми данными, старая сессия отклоняется. При недоступном Vault вход и защищённые запросы отклоняются. Проверить отсутствие пароля в логах, хранилищах вне Vault и ответах сервера.
9. При включённых globals проверить буквальное отображение настроенной служебной базы, включая значение по умолчанию при отсутствии поля. Проверить direct и staged при отказе выгрузки globals.
